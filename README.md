## Understanding the Issue

### Problem Description

Rust's `Path::exists()` checks whether a file exists by making a syscall to the OS. If code then immediately calls `Path::metadata()` on the same path, that triggers a *second* syscall. Between these two calls, the file system could change — for example, another process could delete or replace the file. This is a classic **Time-Of-Check to Time-Of-Use (TOCTOU)** race condition bug. The issue requests a new Clippy lint that detects this pattern and warns developers about it.

### Expected Behavior

The lint should detect code like:

```rust
if new_path.exists() {
    let md = new_path.metadata().unwrap();
    // ...
}
```

And suggest that it be simplified to:

```rust
if let Ok(md) = new_path.metadata() {
    // ...
}
```

This refactored version only makes **one** syscall, eliminating the race condition entirely.

### Current Behavior

Clippy currently has no lint that catches this pattern. Code that calls `Path::exists()` followed by `Path::metadata()` (or similar path operations) compiles and runs without any warning, even though it introduces a subtle TOCTOU bug.

## Solution Approach

### Analysis

There's no existing lint for this pattern — the fix is to build one. The lint needs to detect an `if` expression whose condition is a call to `.exists()` on a `Path`-like receiver, where the body of that `if` block then calls `.metadata()` on the same receiver. The most structurally similar existing lint is `pathbuf_init_then_push`, which also tracks sequential operations on a path receiver across statements. The key difference is that our lint's primary trigger is an `if` expression, so the entry point is `check_expr` matching `ExprKind::If` rather than a state machine across statements.

### Proposed Solution

A new `LateLintPass` registered as a standalone lint (not inside `methods/`) that:
1. Matches `if <cond> { <then_block> }` where `cond` is a call to `.exists()` on a `Path` or `PathBuf` receiver
2. Checks whether `then_block` calls `.metadata()` on the same receiver using `SpanlessEq` for comparison
3. Emits a warning with a suggestion to replace both calls with `if let Ok(md) = path.metadata()`

### Implementation Plan

**Understand:**

Two variants of the pattern to detect:

```rust
// Variant A — if guard
if path.exists() {
    let md = path.metadata()?;
}

// Variant B — sequential statements
let exists = path.exists();
if exists {
    let md = path.metadata()?;
}
```

Suggested fix for both:

```rust
if let Ok(md) = path.metadata() {
    // use md
}
```

**Match:**

`pathbuf_init_then_push` (`clippy_lints/src/pathbuf_init_then_push.rs`) is the closest structural reference — it detects two sequential operations on a path receiver and is registered as a standalone `LateLintPass`. For type-checking path receivers, `path_buf_push_overwrite.rs` and `path_ends_with_ext.rs` show the `is_diag_item(cx, sym::Path)` pattern to follow.

**Plan:**

1. Scaffold the lint:
   ```bash
   cargo dev new_lint --name=path_exists_then_metadata --pass=late --category=nursery
   ```
   This creates `clippy_lints/src/path_exists_then_metadata.rs`, adds the module entry and registration in `lib.rs`, and stubs out `tests/ui/path_exists_then_metadata.rs`.

2. Declare the lint in the new file using `declare_clippy_lint!` with full documentation (What it does, Why is this bad?, Example, Use instead).

3. Implement `check_expr` on the `LateLintPass` to match `ExprKind::If`, extract the condition's receiver and method name, verify the receiver type is `Path`/`PathBuf`, and check the then-block for a `.metadata()` call on the same receiver via `SpanlessEq::new(cx).eq_expr()`.

4. Implement helper functions:
   - `method_call_name` — extracts receiver + method name from `ExprKind::MethodCall`
   - `is_path_receiver` — type-checks the receiver using `is_diag_item`
   - `block_calls_metadata_on` — walks the then-block for a matching `.metadata()` call
   - `build_suggestion` — constructs the replacement string

5. Register in `lib.rs` — add `mod path_exists_then_metadata` and `store.register_late_pass(...)`.

6. Write UI tests covering positive cases (basic `if path.exists()` + `path.metadata()`, PathBuf variant) and negative cases (exists without metadata, metadata on a different path, metadata outside the if block).

7. Run `TESTNAME=path_exists_then_metadata cargo uibless` to generate `.stderr` and `.fixed` files.

### Manual Testing

Full `cargo test` passed cleanly with zero failures at each round. `cargo dev update_lints`, `cargo dev fmt`, and `cargo dev dogfood` were run before each round of commits.

### Known Limitations

- Does not detect `fs::` free functions (e.g. `fs::read(path)`, `fs::File::open(path)`), only method calls on the path receiver itself.
- Does not detect `try_exists()` used with `.unwrap()`/`.unwrap_or(false)` — only the `?` form is supported.
- For the stored-bool variant, only detects when the `if` immediately follows the `let` (no intervening statements).

These are documented in the `### Known problems` section of the lint doc block.

## Implementation Notes

### Week 3 Progress

**What I built:**

A new Clippy lint — `unnecessary_path_exists` in the `nursery` category — that detects the TOCTOU pattern where `Path::exists()` is used as an `if` condition immediately before a filesystem operation on the same path inside the block body. The lint name changed from the original plan (`path_exists_then_metadata`) after reviewing the issue more carefully. The scope turned out to be broader than just `metadata` — any redundant fs syscall qualifies. Looking at how similar lints are named (`unnecessary_first_then_check`, `unnecessary_get_then_check`) made it clear the convention is to name the unnecessary operation, which led to `unnecessary_path_exists`.

**Challenges faced:**

- `is_diag_item()` is an extension method from `clippy_utils::res::MaybeDef`, which isn't imported by default. The first build failed because of this missing import — the compiler error pointed at it clearly, but it wasn't obvious upfront since other lints pull it in implicitly through their module structure.

**Detected fs methods (final, after Round 4):** `metadata`, `symlink_metadata`, `canonicalize`, `read_link`, `read_dir`, `is_file`, `is_dir` (`is_symlink` removed — see Round 4)

## Round 2: Review Feedback (samueltardieu)

The PR got two comments from a maintainer on the first pass:

1. **Category: don't use `nursery`.** "You need to choose a category, nursery is where lints go to die nowadays." `nursery` is meant for lints that are still buggy/unfinished, and almost nobody enables the whole group, so lints parked there get little real-world usage and tend to sit unmaintained. Since this lint flags a real bug pattern with no legitimate reason to write it intentionally, and the open issues are missed detections rather than false positives on valid code, `suspicious` (warn-by-default) was the better fit. Changed `nursery` → `suspicious` in the `declare_clippy_lint!` block.

2. **Restructure + move to `methods/`.** "Rather than checking each and every block, it probably would be more efficient to first check for a call to the `.exists()` method and then analyze the surrounding block. This lint should probably be moved into the methods directory." The original implementation was its own `LateLintPass` with `check_expr`/`check_block`, meaning it ran on every expression and block in the crate before even checking whether an `.exists()` call was involved. `clippy_lints/src/methods/mod.rs` already runs one shared `LateLintPass` (`Methods`) that visits every method call once and dispatches by name. Moved the lint to `clippy_lints/src/methods/unnecessary_path_exists.rs` and added a `(sym::exists | sym::try_exists, [])` match arm, so the lint only activates on actual `.exists()`/`.try_exists()` calls — then climbs outward via `get_parent_expr`/`get_enclosing_block` rather than scanning inward from every block.

Verified the inversion didn't change any observable behavior — same 18 diagnostics, byte-for-byte, before and after the restructure.

### Self-Review After the Restructure

Inverting the traversal direction silently dropped two guards that were implicit in the old code:

- **Missing type guard.** The new dispatch arm triggered on any type's `.exists()` method, not just `Path`. Fixed by gating on `is_path_method_call(cx, expr)` first. Added a regression test (`check_unrelated_exists_method`) with a custom type that has unrelated `exists`/`metadata` methods.
- **Missing expansion guards.** The old `check_expr`/`check_block` each had `if span.from_expansion() { return; }` guards that were silently dropped when the traversal was inverted. Re-added at the point where each node is discovered.

### `try_exists()` Support

`Path::try_exists()` (stabilized 1.63) returns `io::Result<bool>` and is typically used as `if path.try_exists()? { ... }`. The `?` desugars in HIR to `Match(Call(<Try::branch lang item>, [inner_expr]), _, MatchSource::TryDesugar(scrutinee_hir_id))` — confirmed against rustc's own lowering code (`rustc_ast_lowering::expr::lower_expr_try`).

- Added `try_exists` to `clippy_utils/src/sym.rs` and dispatched it alongside `exists` in `methods/mod.rs`
- Added `peel_try_desugar`/`peel_try_desugars` helpers matching on `MatchSource::TryDesugar` by `HirId` comparison
- Covers both the direct-condition path and the stored-bool path
- `.unwrap()`/`.unwrap_or(false)` forms left as a documented known limitation to avoid false positives

## Round 3: Review Feedback (samueltardieu, second pass)

Two false positives reported with concrete repros:

```rust
// non-place receiver: no guarantee dyn_path() returns the same path twice
if dyn_path().exists() {
    let _ = dyn_path().metadata().unwrap();
}

// reassigned receiver: path_clone has changed by the time metadata() is called
let mut path_clone = PathBuf::from(path);
if path_clone.exists() {
    path_clone = PathBuf::new();
    let _ = path_clone.metadata().unwrap();
}
```

**Root cause:** `SpanlessEq` is a purely structural comparison — "do these two chunks of code have the same shape," not "does evaluating this code twice produce the same value." Two calls to `dyn_path()` look identical in the AST even though nothing guarantees the function returns the same thing twice.

**Fix:** `find_fs_call` now calls `path_to_local_with_projections` on the `.exists()` receiver before doing anything else. If the receiver isn't a local variable — optionally through field/index projections — the search bails: a function call has no stable value to reason about. The search also now watches for an `Assign` to the tracked local occurring before the matching fs call, and bails if one appears. An additional check via `cx.typeck_results().expr_ty_adjusted(recv).is_mutable_ptr()` catches mutating method calls (e.g. `.push()`) on the same receiver — a type-based check rather than a hardcoded list of method names.

New tests: `check_call_receiver`, `check_reassigned_receiver`, `check_mutated_receiver`, `check_mutated_receiver_after_fs_call`.

## Round 4: Review Feedback (Jarcho)

**1. Simplify `is_path_method_call`.**
Applied verbatim: `cx.typeck_results().type_dependent_def_id().opt_parent(cx).opt_impl_ty(cx).is_diag_item(cx, sym::Path)` — replacing a manual `tcx.parent` + `tcx.type_of` sequence with chainable `clippy_utils::res::MaybeDef` methods.

**2. Check `recv` is a projection first.**
`iter.next()?.exists()` followed by `iter.next()?.metadata()` shouldn't lint — same root cause as Round 3. Covered by the same `path_to_local_with_projections` gate. New test: `check_iterator_receiver`.

**3. Rewrite using `for_each_expr`.**
Rewrote `find_fs_call`/`find_fs_call_in_expr` — previously two functions manually iterating statements and peeling method chains — into a single function built on `for_each_expr_without_closures`. The `_without_closures` variant was chosen specifically because code inside a closure body isn't provably part of the `if`'s control flow. New test: `check_closure_deferred`.

Side effect: the old manual loop only scanned top-level statements in the `then` block, never descending into nested `if`s. `for_each_expr_without_closures` doesn't have that limitation — nested control flow is now searched too. Running `cargo dev dogfood` surfaced a real instance in Clippy's own `clippy_dev/src/setup/vscode.rs`:
```rust
if vs_dir_path.exists() {
    if !vs_dir_path.is_dir() {
```
Marked with `#[expect(clippy::unnecessary_path_exists)]` initially, then fixed properly (see "Follow-up: `vscode.rs` TOCTOU" below).

**4. `is_symlink` doesn't mean the same thing as `exists()`.**
"`is_symlink` on the other hand doesn't even refer to the same thing since it won't resolve the item if it is a symlink." Removed from the tracked method list entirely. Its `sym::is_symlink` entry became unused and was removed from `clippy_utils/src/sym.rs` (caught by the repo's own `symbols-used` test). Its old "should lint" test case moved into the false-positive block with an explanatory comment. Help text also made conditional: `is_dir`/`is_file` return `bool` with no error to handle, so they now get pointed at `metadata()` instead of the generic "handle the error directly" message.

## Follow-up: `vscode.rs` TOCTOU (self-identified via dogfood)

Rewrote `check_install_precondition` to call `fs::create_dir` unconditionally and match on the `Result`, instead of checking `exists()` up front:

```rust
match fs::create_dir(vs_dir_path) {
    Ok(()) => { /* didn't exist, now created */ return true; },
    Err(err) if err.kind() == ErrorKind::AlreadyExists => {},
    Err(err) => { /* real creation failure */ return true; },
}
if !vs_dir_path.is_dir() { /* ... */ }
```

This collapses the common "doesn't exist yet" path from two racy syscalls into one atomic `create_dir` call. The `#[expect]` was removed once the fix was in. Verified behavior across all five real branches by hand: fresh install, blocked reinstall, forced reinstall, removal, and the "exists but is a file" error path.

## Learnings & Reflections

### Technical Skills Gained

The biggest thing was getting hands-on with Clippy's tooling — how lints are scaffolded, how the HIR is structured, and how `cargo dev` automates registration boilerplate. Working that close to the compiler internals was new territory coming from application-level Rust.

The restructure round added another lesson: inverting how a lint discovers its target (top-down scan vs. bottom-up climb) is easy to get right on the happy path while silently dropping guard clauses that were implicit in the old traversal. Re-reviewing the diff line-by-line — not just re-running tests — was what caught both gaps.

The recurring theme across rounds 3 and 4: a structural check (`SpanlessEq`) can answer "do these two things look the same" while still being wrong, when the real question is "are these provably the same value at a point where nothing could have run in between." Three separate false positives (`dyn_path()`, reassignment, mutation) all traced back to that one gap. The fix in each case was adding a check for value stability, not just syntactic similarity.

The other recurring theme: dogfooding surfaced things test cases alone didn't. The `vscode.rs` TOCTOU instance and the `unused_trait_names` CI failure both came from running the tool against real code — neither would have been caught by only re-running `tests/ui/unnecessary_path_exists.rs`.

### Challenges Overcome

Thinking through edge cases was harder than understanding the bug itself. The TOCTOU race made sense immediately, but mapping out all the ways it could appear in real code — the `?` operator desugaring, compound `&&` conditions, the stored-bool variant, non-place receivers, mutations — took more iteration than expected. Each one required digging into how Rust represents that pattern in the HIR.

### What I'd Do Differently Next Time

For a second contribution I'd probably look for a different issue or project — not because this one went badly, but because starting fresh somewhere new would push me to apply what I learned here rather than staying in familiar territory.
